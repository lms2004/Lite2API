# Lite2API：面向个人开发者的轻量 AI API 网关

## 〇 摘要

**一句话定位：** 为需要调用多个 AI 渠道的个人开发者提供统一网关，解决接入分散、故障等待和单人维护问题；在同机、相同 30 秒等待上限的本地“无账号、无路由”调度对照中，将返回耗时从约 30 秒降至 1 毫秒以内。

**时间：** 2026 年 8—9 月，按仓库可见开发记录界定；本文补充验证日期为 2026 年 10 月 27 日。**团队规模：** 1 人。**负责范围：** 网关核心、管理台、渠道适配集成与部署验证；OAuth、Cookie 和特定上游协议复用外部适配器。

- **痛点：** 个人开发者需要混用 API Key、OAuth 和 Web 会话渠道，既要反复维护接入配置，又会在不可用渠道上浪费等待时间，历史实测中一次无 Rerank 候选的请求等待了 30,071 毫秒才返回失败。
- **不足：** 继续使用完整中转平台需要承担个人场景用不到的平台能力，直接连接各渠道又会把认证、换号和排障留给客户端，而进程健康或凭据已导入也不能证明推理可用。
- **目标：** 在单机、单管理员范围内统一接入，静态不可用时快速失败，明确拒绝时安全换号，并保留流式正确性、密钥隔离和有界资源占用。
- **做法：** 采用稳定模型别名与按能力筛选的隔离适配器、按提交确定性划分的故障切换，以及内存快照和有界观测组成的轻量核心。
- **价值：** 历史上完成 8 个实际账号的分类迁移，并有 Chat、Responses、Embeddings、Images 的真实成功记录；本次对照验证了无候选调度从 30 秒级降至 1 毫秒以内，当前回归同时验证了明确拒绝后切换、不确定提交不重放及准入拒绝时请求体零读取。

历史 Rerank 耗时用于说明痛点，改善数值来自另一组无账号、无路由的同场景版本对照，两者不是同一次线上请求的前后结果。延迟改善仅指本地调度，不代表模型响应速度或线上 P95；迁移完成也不等于全部凭据可用。[迁移与实测依据](/root/Lite2API/docs/INTERFACE_AUDIT_2026-08-14.md:29)；[本次对照原始数据](/root/Lite2API/docs/evidence/no-candidate-wait-2026-10-27.json)。

## 一 业务背景（Why）

### 1 用户与场景

项目面向在自有服务器上调用多个 AI 渠道的个人开发者。使用者需要在聊天、编程工具、向量化和图片生成等任务之间切换，同时维护 API Key、OAuth、setup/refresh token 等不同凭据。

仓库保留的真实接口审计覆盖了这些请求：通过 Chat 接口调用 Gemini、通过 Responses 调用 Codex 渠道、调用 Embeddings 返回向量，以及通过 Images 生成图片。2026 年 8 月 14 日记录的单次端到端耗时分别为 Chat 非流式 527 毫秒、Responses 807 毫秒、Embeddings 349 毫秒和 Images 24,031 毫秒；这些记录证明接入链路实际跑通过，不用于推导性能提升。[真实调用表](/root/Lite2API/docs/INTERFACE_AUDIT_2026-08-14.md:72)

### 2 痛点与代价

**痛点 A：使用模型之前，先要处理渠道和凭据差异。** 旧系统有 8 个实际账号，覆盖 API Key、OAuth 和 token 等类型；凭据需要落到不同认证运行环境，不能把“导入一个文件”当成“完成接入”。使用者需要一个稳定入口，并知道某个渠道到底能处理哪类请求。维护代价可表示为“账号规模 × 每账号变更频率 × 单次配置和验证耗时”；仓库能确认账号规模为 8，但没有后两项的统计，因此不估算节省工时。

**痛点 B：已经无法执行的请求仍在等待，失败后又难判断能否重试。** 历史实测中，无 Rerank 候选的请求耗时 30,071 毫秒后返回 503，Claude 认证失败也等待约 30.2 秒。前一种场景每发生一次就占用约 30 秒无效等待；若发生 K 次，累计代价约为 K × 30 秒，实际频率未采集。另一方面，上游返回错误时可能已经接受请求，自动换号会引入重复执行或重复计费风险，仓库没有证明实际发生过重复扣费。

**痛点 C：一个人既要维护服务，也要判断它是否真的可用。** 当时所有已安装服务的健康 URL 都返回 200，但真实推理中仍出现 Claude 401、Gemini CLI 403 和 Grok 401。使用者仍需排查凭据、模型和路由，单看进程状态无法决定是否可用；日志、请求体和外部依赖也必须受限，避免维护工具本身成为额外负担。其代价是“排障或升级次数 × 单次处理耗时”，当前没有工时和事故频率数据，本文以可核查的运行边界和状态行为评价改进。[故障与健康差异](/root/Lite2API/docs/INTERFACE_AUDIT_2026-08-14.md:102)

### 3 现有应对及其不足

继续使用完整 Sub2API，可以复用已有账号管理，但项目实际只需要单机转发、账号池和调度，不需要余额、套餐、支付、多租户与用户系统。Lite2API 因此选择独立实现这一子集；仓库没有同负载的两套系统资源对照，不能声称已经证明某个资源下降比例。

让客户端直接连接各个 API 或适配器，可以减少一层网关，但客户端需要自行处理入口、模型名、凭据和故障切换。仅统一 Base URL 也不够：同名模型不一定支持相同端点，适配器进程存活也不等于具有有效凭据。

最终选择保留轻量网关，复用外部认证适配器，集中管理路由和故障语义。[项目取舍](/root/Lite2API/README.md:1)；[适配器边界](/root/Lite2API/docs/ADAPTER_DESIGN.md:3)

## 二 项目定义（What）

### 5 问题陈述

让个人开发者在单机调用多个 AI 渠道时，不再反复处理每个渠道的接入与换号逻辑，并能及时区分“暂时满载”“当前不可用”和“请求结果不确定”。

### 6 范围

项目覆盖统一模型 API 入口、模型别名与渠道能力映射、账号调度与并发限制、流式转发、熔断和安全换号，以及账号接入、客户端 Key、请求摘要和运行状态管理。官方兼容 API 使用内置转发；OAuth、Cookie 和私有协议由隔离适配器承担。

范围止于单机、单管理员。项目不提供商业计费、支付、多租户、团队权限和多节点一致性，也不在通用调度器中自动转换任意协议。外部凭据能否获得平台权限、上游是否支持某种模型能力，仍由对应上游决定。

### 7 成功标准

以下标准按用户可感知结果组织；其中数值阈值来自现有实现或测试契约，不追溯宣称为项目立项时已制定的 KPI。

| 对应痛点 | 用户可感知结果 | 指标与基线 | 验收标准 |
|---|---|---|---|
| A：接入分散 | 同一协议的客户端使用稳定网关入口与别名，渠道调整在网关侧完成 | 旧系统有 8 个实际账号，认证类型和落地位置不同 | 迁移有去向和状态记录；逻辑模型可解析到兼容渠道；不同操作不会误选不支持的账号 |
| B：无效等待 | 没有候选时及时得到失败，满载时才有界等待 | 历史无 Rerank 候选请求为 30,071 毫秒；旧调度器未区分无候选与等待容量 | 无候选直接返回；已有静态操作不兼容测试要求 100 毫秒内退出；通过相同等待上限的前后版本对照验证 |
| B：重试风险 | 明确拒绝可自动切换，结果不确定有明确提示 | 基线审计识别出不确定提交后重放风险，缺少线上事故率 | 明确拒绝夹具命中备用目标 1 次；不确定提交夹具命中备用目标 0 次；客户端不能伪造内部重试证明 |
| C：维护与判断负担 | 核心依赖少，资源有边界，状态能表达真实失败与未知 | 存在健康 200、实际推理失败的记录；早期准入前读取请求体 | 核心不依赖数据库或 Redis；准入拒绝时请求体读取为 0；流中断计为失败；没有可信观测时显示未知 |

**不能牺牲的约束：** 不把两个上游流拼成一次响应；不因热加载丢失在途请求的并发占用；管理凭据、客户端 Key 和上游凭据相互隔离；请求摘要不保存提示词、图片或响应正文。

### 8 难点

**难点 H1，对应痛点 A：统一调用与上游差异同时存在。** 相同模型名不保证端点、推理强度或认证方式相同；统一入口必须保留这些差异，否则就会把不兼容请求送到错误渠道。

**难点 H2，对应痛点 B：更积极的恢复与执行确定性存在冲突。** 无候选和满载都表现为“选不到账号”，但只有后者值得等待；上游出错和未接受请求也不是同一件事，自动恢复必须避免制造第二次执行。

**难点 H3，对应痛点 C：轻量运行与状态正确性必须同时满足。** 单机不希望增加数据库和常驻轮询，但并发、热加载、长流、凭据撤销及真实健康证据都有各自生命周期；仅限制请求数量或展示 HTTP 200，无法完整表达这些边界。

## 三 方案（How）

### 9 方案总览

最终系统由一个 Go 网关和按需启用的外置渠道适配器组成。客户端请求先经过 Key 策略、总并发和请求体预算，再按操作类型、逻辑模型与渠道能力筛选目标；调度器取得账号并发槽后，通过账号独立连接池访问上游，并根据提交确定性决定返回、换号或报告不确定结果。管理台负责账号、路由和 Key 配置，运行配置通过内存快照整体切换，观测数据通过有界缓冲和摘要日志保存。

```text
客户端 → Key/并发/字节预算 → 操作与模型能力筛选 → 账号调度
                                                  ↓
管理台 → 原子配置/运行快照                  账号独立连接池
                                                  ↓
                                    兼容 API / 隔离认证适配器
                                                  ↓
                                       响应、流或明确失败结果
                                                  ↓
                                      有界摘要与路由健康证据
```

### 10 核心决策

**决策 D1：用稳定别名表达调用意图，用能力契约和隔离适配器承接差异。对应 H1。** 路由声明逻辑模型和推理强度，真实渠道声明支持的操作及模型映射；调度前先做兼容性筛选。API Key 兼容端点由核心处理，OAuth 和 Cookie 凭据分别交给外置适配器保存、刷新。

没有选择按模型名称猜协议，也没有把各类认证与私有协议全部放入网关。前者不能证明端点兼容，后者会扩大单人维护的变化范围。局部结果是，旧系统 8 个账号都有明确迁移归属；当前回归覆盖了同一逻辑模型在不同真实渠道中的解析和操作类型筛选。迁移中上游拒绝的凭据仍记录为不可用，不计入成功推理渠道。[迁移去向](/root/Lite2API/docs/INTERFACE_AUDIT_2026-08-14.md:29)；[操作筛选测试](/root/Lite2API/internal/gateway/runtime_test.go:356)；[模型映射测试](/root/Lite2API/internal/gateway/runtime_test.go:540)

**决策 D2：把是否等待、是否换号建立在明确的失败语义上。对应 H2。** 调度器区分无兼容候选、账号不可用和容量占满，只有容量阻塞才等待释放。明确拒绝的 401/402/403/429、显式目标的模型 404，以及可证明未写入上游的连接失败可切换目标；普通上游的 408/409/425/5xx 和写入后断连，返回 `uncertain_submission`，不自动跨账号重放。流已开始后中断，也不切换到另一个上游续接。

没有选择所有失败统一排队或所有 5xx 自动换号：前者拖延确定失败，后者不能排除重复执行。一个受限例外是，配置指定凭据的受信 CLIProxyAPI 适配器能提供“尚未提交”的内部证明时，允许对应失败继续切换；客户端输入的同名标记会被剥离。

局部结果是，本地无候选对照从约 30 秒降至 1 毫秒以内；现有夹具验证明确拒绝后备用目标收到 1 次请求、不确定提交后收到 0 次请求。这里证明的是调度和重试行为，尚无线上重复计费下降率。→ 见 P1。[调度实现](/root/Lite2API/internal/gateway/runtime.go:637)；[提交确定性策略](/root/Lite2API/internal/gateway/gateway.go:1727)；[受信证明测试](/root/Lite2API/internal/gateway/gateway_test.go:1332)

**决策 D3：以单机内存状态保持轻量，同时明确资源所有权和观测依据。对应 H3。** 核心使用不可变配置与 Key 快照，热路径不读取数据库或磁盘；在准入后读取请求体，并将读取、解析和改写占用纳入字节预算，流结束后才释放相关并发槽。观测侧区分进程存活与路由可用，以实际 `Outcome` 和绑定配置身份的路由证据判断结果，避免把已发出 200 的断流记成成功。

没有为单机引入 Redis 和独立监控服务，也没有依赖无限日志或高频探测换取可见性。最近请求固定保留 512 条，摘要日志默认约 24 MiB；适配器目录按需探测，整体预算 750 毫秒；无可信 usage 或额度时保留未知状态。

局部结果是，Key 并发或请求体预算拒绝的回归中，请求体读取次数均为 0；流中断统计为失败；低流量路由的失败证据不会因为最近请求环被其他流量挤满而丢失。这些结果支撑运行可控和判断准确，没有用来推算排障工时下降。→ 见 P2、P3。[运行状态与安全边界](/root/Lite2API/docs/ARCHITECTURE.md:24)；[零读取测试](/root/Lite2API/internal/gateway/gateway_test.go:468)；[断流结果测试](/root/Lite2API/internal/gateway/stats_test.go:54)；[路由证据测试](/root/Lite2API/internal/gateway/operations_test.go:153)；[日志边界](/root/Lite2API/docs/OPERATIONS.md:149)

## 四 关键过程

### P1 从“上游失败就换号”转向“先确认是否可能已执行”——支撑 D2

生成请求收到 5xx 或写入后断连时，客户端只看到失败，很容易将其当成应当换号的信号；但错误状态不能证明上游没有接受任务。针对这种风险，验证把“明确拒绝”“写入前失败”和“不确定提交”拆成独立夹具，检查备用上游实际收到几次请求。原因由此落到提交确定性，而不是错误码是否严重：最终策略对不确定提交停止重放，对明确拒绝继续切换。后续指定凭据路由进一步引入受信的未提交证明，使确实未提交的适配器失败仍可恢复，同时禁止客户端伪造证明。当前夹具分别验证了不确定提交后备用调用 0 次、明确拒绝或可信未提交后备用调用 1 次。[不确定提交测试](/root/Lite2API/internal/gateway/gateway_test.go:218)；[明确拒绝测试](/root/Lite2API/internal/gateway/gateway_test.go:246)；[可信证明测试](/root/Lite2API/internal/gateway/gateway_test.go:1332)

### P2 从“限制请求数”转向“跟踪实际持有的字节和生命周期”——支撑 D3

早期实现已有请求大小和并发限制，但架构审计发现，请求体会在真正的准入检查前被读取，读取、解析和改写还会产生不同生命周期的副本。因此，仅限制请求数不能证明内存受控；在队列等待或传输层异步关闭期间提前释放预算，也可能低估实际占用。最终将读取放到完整准入之后，以字节租约覆盖实际副本，并让释放时机跟随真实所有权。回归直接统计请求体读取次数：当 Key 并发已满或字节预算已用尽时，均在读取 0 次的情况下拒绝请求。该结果证明门禁顺序与资源约束生效，历史审计中的理论内存放大量不作为生产峰值。[问题分析](/root/Lite2API/docs/CODE_ARCHITECTURE_DEEP_AUDIT_2026-08-30.md:202)；[最终资源所有权](/root/Lite2API/docs/CODE_ARCHITECTURE_OPTIMIZATION_2026-08-30.md:38)；[回归依据](/root/Lite2API/internal/gateway/gateway_test.go:468)

### P3 从“进程健康、HTTP 200”转向“当前路由的真实结果”——支撑 D3

真实审计已出现服务健康 200、推理却返回 401 或 403 的情况；流式请求还可能先发送 200，再在传输中失败。由此可见，进程可达和响应头状态都不足以判断调用成功。最终以 `Outcome` 统一结果口径，拆分存活与就绪状态，并单独保留绑定路由配置身份的最新证据。验证分别构造“200 后断流”和“低流量失败路由被大量其他请求挤出最近记录”的情况，结果仍计为失败或保持不可用；没有新观测的路由也不会被表述为已经验证成功。这提高了状态可信度，但没有直接证明定位耗时下降。[断流统计测试](/root/Lite2API/internal/gateway/stats_test.go:54)；[路由证据保留测试](/root/Lite2API/internal/gateway/operations_test.go:153)

### 13 业务收益与归因

项目已兑现的直接价值是：把多渠道调用中的接入、调度、故障和观测收进一个单人可维护的网关，并用明确行为消除静态无候选等待、限制不确定提交重放、减少状态误判。这里的轻量收益体现为核心部署依赖减少和运行边界可检查，尚未换算为月度节省金额或工时。

历史资源快照记录 Lite2API 约 1.99 MiB、CLIProxyAPI 约 11.33 MiB，可说明当时两个组件的轻量运行状态；它们不是全系统峰值，也没有旧系统同负载对照，因此不计算内存下降比例。真实接口耗时同时受网络、模型和适配器影响，本文只将隔离调度对照的改善归因于调度逻辑。[资源快照](/root/Lite2API/docs/INTERFACE_AUDIT_2026-08-14.md:172)

尚未兑现的目标包括完整的“模型 × 操作 × 特性”能力矩阵、完整 half-open 单探针熔断，以及所有历史环境变量 Key 与托管 Key 的策略一致性；灾备脚本也不能替代完整恢复演练。因此，本项目的价值结论限定为单机网关的接入整合、调度正确性和有界运行，不扩展为商业平台能力或线上高可用承诺。[已记录的剩余边界](/root/Lite2API/docs/CODE_ARCHITECTURE_OPTIMIZATION_2026-08-30.md:249)
